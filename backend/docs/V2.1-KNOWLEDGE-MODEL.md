# V2.1 — Career Knowledge Model

Scope: **V2.1 = KNOWLEDGE MODEL only.** This phase turns V1's hardcoded
`src/data/careerPaths.js` / `src/data/skills.js` into persistent,
queryable reference data. It introduces no scoring, matching, evidence,
AI assessment, dynamic roadmap or agent behavior — those are later
phases (see "Roadmap" below). The architecture principle this and every
later phase must preserve:

> **The LLM talks. The deterministic engine decides.**
> AI never invents match scores, readiness scores, skill gaps,
> confidence scores, career compatibility, roadmap completion, or
> evidence state. Those come from deterministic backend/domain logic.

## Domain model

All in the new `com.pathos.knowledge` package, alongside V2.0's
`com.pathos.user`/`com.pathos.profile` (untouched):

- **SkillCategory** — a grouping for skills (e.g. "Cloud", "DevOps"). Pure reference data.
- **Skill** — a canonical skill. `canonicalName` is the trimmed/lowercased form of `name`, computed in Java (`Skill.normalize`), used for exact-match lookups. `aliases` is a JSON-array-in-TEXT column (same representation V2.0 used for `Profile.skills`, factored into a reusable `com.pathos.shared.StringListConverter`). Arbitrary user-entered strings never become a new canonical Skill automatically — only seed data does today.
- **CareerRole** — a persistent career path (was a hardcoded entry in V1's `PATHS` map). `domain` is a free-text label, deliberately not a FK to `SkillCategory` (a role's domain and a skill's category are different classifications).
- **RoleRequirement** — one (role, skill) edge: `requirementType` is `REQUIRED` or `PREFERRED`, `weight` is 1–10 importance. This is knowledge only — no compatibility score is computed here; that's V2.2.
- **SkillRelationship** — a directed skill-graph edge: `PREREQUISITE_OF` / `RELATED_TO` / `TRANSFERABLE_TO`, with a 1–10 weight. Plain PostgreSQL relational rows — **not** a graph database (no Neo4j, per architecture discipline).
- **CareerTransition** — hand-curated knowledge about moving from one `CareerRole` to another: `difficulty` (`LOW`/`MEDIUM`/`HIGH`) and a short `rationale`. No dynamic recommendation logic.
- **LearningResource** — a small curated set of resources (title/provider/url/type/difficulty), each optionally linked to one `Skill`. Not a marketplace, not scraped.

## API

All **public** (no JWT required — see `SecurityConfig`'s `permitAll` for
`GET` on these three prefixes). This is deliberate: career knowledge
carries no user data, and requiring auth would only break V1's existing
anonymous career-path browsing for no security benefit. Profile endpoints
are unchanged and still require authentication.

| Method | Path | Returns |
|---|---|---|
| GET | `/api/skill-categories` | all skill categories |
| GET | `/api/skills` | all active skills |
| GET | `/api/skills/{id}` | one skill (404 `SKILL_NOT_FOUND` if unknown) |
| GET | `/api/career-paths` | all active career roles |
| GET | `/api/career-paths/{id}` | one role (404 `CAREER_ROLE_NOT_FOUND` if unknown) |
| GET | `/api/career-paths/{id}/requirements` | that role's `RoleRequirement`s |

No write endpoints exist for this data — it's seeded via Flyway only.
`GlobalExceptionHandler` now also maps a malformed path-variable id
(`MethodArgumentTypeMismatchException`) to `400 VALIDATION_FAILED`
instead of falling through to the generic 500 handler.

## Seed data

Sourced from V1's own `src/data/careerPaths.js` / `src/data/skills.js`
wherever possible (same role names, same skill groupings, same blurb
text), not invented. `core` skills became `REQUIRED` (weight 9), `next`
became `PREFERRED` (weight 6, minus anything already `REQUIRED`), `later`
became `PREFERRED` (weight 3, minus anything already listed). Three
skills V1 referenced in `careerPaths.js` but never put in a
`SKILL_GROUPS` category (`Observability`, `MLOps`, `Multi-cloud design`)
were added using their existing V1 blurb text. The skill-relationship
graph and role transitions are a small, conservative, hand-picked set —
not a claim to model the full job market.

## Migration strategy: V2.0 profile skills → canonical skills

**`Profile.skills` is unchanged.** It is still the V2.0 free-text
`List<String>` column; no Flyway migration here touches `profiles` at
all, and no existing profile data is rewritten.

Instead, `SkillNormalizationService` (`com.pathos.knowledge`) provides a
read-only, additive lookup: given a profile's existing raw skill
strings, which match a canonical `Skill` (by exact name or alias,
case/whitespace-insensitive) and which remain **unmapped user claims**.
An unmapped skill is never discarded, rewritten, or flagged as an error —
it's returned exactly as entered. Matching is deliberately conservative:
no fuzzy matching, no guessed mappings for ambiguous terms (e.g. "Java"
and "JavaScript" never cross-match).

The actual switch of `Profile` persistence to canonical skill ids is
intentionally **not done in V2.1** — it's deferred to V2.2, when the
matching engine will actually need canonical ids as input (which is also
when evidence/proficiency, also out of V2.1's scope, will be designed).
Building that switch now, before anything consumes it, would be
premature and would risk the "don't silently destroy existing profile
data" constraint for no present benefit.

## Frontend

`src/api/knowledgeApi.js` wraps the six public endpoints.
`useCareerKnowledge` fetches career-path descriptions once, keyed by
path name (matching how V1 already identifies paths everywhere). Wired
into `CareerUniverse` as one optional, additive line of description text
under the match badge — shown only when the backend provided one.

V1's `src/data/careerPaths.js`, `src/data/skills.js`, and
`src/utils/scoring.js` are **all untouched** and remain the actual
source of truth for match scoring, skill groupings, and the Skill
Gap/Learn Next/Compare Paths/Roadmap/What-If/Project Builder views. If
the knowledge API is unreachable, `useCareerKnowledge`'s descriptions map
just stays empty and the UI renders exactly as V1 always did — verified
by `npm test` (24/24) and `npm run build`.

## Known limitations

- **Not executed against PostgreSQL in this environment.** Maven
  Central is still blocked by the sandbox's egress policy (403), exactly
  as in V2.0 — see root `backend/README.md`. All V2.1 migrations, entity
  mappings, and tests are written and internally consistent but have not
  been run anywhere in this process. Do not treat any of it as more than
  that until it's actually executed against real PostgreSQL (via `mvn
  test` / `mvn spring-boot:run`, per the earlier Windows verification
  handoff).
- No admin/write tooling exists for this data yet — it's Flyway-seeded only.

## Explicitly deferred to V2.2+

- Compatibility/match scoring (reading `RoleRequirement`/`SkillRelationship` as input)
- Evidence/proficiency model (claimed vs. demonstrated vs. verified)
- Switching `Profile.skills` persistence to canonical skill ids
- Conversational AI assessment, dynamic roadmap intelligence, progress intelligence, AI agent behavior
- Any admin/write API for career knowledge
